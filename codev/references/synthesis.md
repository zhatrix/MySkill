# synthesis.md — 跨模型综合与门禁

所有外部 agent 返回、逐字呈现之后，由 Claude 做综合。目的：把多个模型的结论收敛成
**一份可执行的结论**，并暴露分歧（分歧往往正是风险所在）。

---

## 0. 参与方为空 / 过少

- **本轮实际参与的【外部】agent = 0**（全部超时/鉴权失败/空输出）：不做矩阵。如实告知用户"所有外部 agent 均
  未返回有效结果"，逐条列出每个 agent 的失败原因，然后基于 G2 `self` 的结果 + Claude 自己的判断给结论，并明确
  标注"无外部交叉验证"。review 模式此时门禁按 Claude 单方结果给，并注明置信度受限。
- **只有 1 个外部 agent 参与**：可出结论，但提示"单一外部模型无交叉验证，置信有限"（self 不算外部）。

## 0.4 发现编号（矩阵之前）

把每家输出里的每条发现编成 `r<轮次>-<agent>-<两位序号>`（如 `r2-codex-03`），按它在原文里的出现顺序编。
本 agent 的两路也编：G1 自查 `r<N>-check-NN`（台账 agent 写 `check`）、G2 自评 `r<N>-self-NN`（台账 agent 写 `self`）——分开记，
`codev_stats` 才能只拿 self 与外部比。
多家提到同一件事时**各自保留编号**，矩阵里并成一行、来源列写全部编号。此后矩阵、裁决、门禁、回归核对、
已驳回清单、发现台账（`codev_finding_add`）全部引用编号——跨轮才对得上号，"上一轮驳回的又被提出来"才能识别。

## 0.5 事实核查回填（**做矩阵之前的必经步骤**）

各 agent 按 prompts.md 的「两档结论」把发现分成 **A. 已查证** 和 **B. 需进一步核实的假设**。
**B 栏不能就这么挂着**——历史上正是这些"看不到代码所以标存疑"的条目变成了孤立的 FAIL，
让整轮评审看起来失败，实际只是没人去查。所以综合前先把 B 栏跑完一遍：

1. **汇总**：把所有 agent 的 B 栏条目合并去重，列成一张核实清单。
2. **路由**（每条选一个执行者）：
   - **Claude 自己核实**——默认选项。直接 Read/Grep 仓库确认，最快最准。
   - **交给 codex**（`codev_bg_native`，有真实仓库权限）——条目多、或需要跨文件追调用链、
     或想要一个独立于 Claude 的第二双眼睛时。
3. **回填**：每条给出 **成立 / 不成立 / 仍无法确定** + 依据（文件:行号）。
   - **成立** → 升级成正式发现，进下面的一致性矩阵，按实际严重级别定 P1/P2/P3。
   - **不成立** → 标注"因 X 而不成立"后**关闭**，不进矩阵、不计入门禁。
   - **仍无法确定** → 保留为遗留项，写清卡在哪。

```
事实核查回填
- ✅ 成立：codebuddy 疑"site_scope 未过滤已归档站点" → 已核对 site_scope.py:42，确无过滤 → 升 P1。
- ❌ 不成立：opencode 疑"字段 status 无索引" → migration 0061 已建复合索引 → 关闭。
- ❓ 待定：并发写入顺序需压测才能判定 → 记为遗留项。
```

⚠️ **门禁只依据已查证的发现**（A 栏 + 回填后"成立"的）。**不得**因为 B 栏还有条目就判 FAIL——
那是把"没查证"误当成"有缺陷"。

## 0.6 P1 采纳前亲验前提（**不分 A/B 栏，不可跳过**）

0.5 只处理 B 栏。但实测 **A 栏"已查证"的 P1 同样翻过车**，且每次翻车都是被采纳后写进文档、下一轮才被另一家推翻：
- "枚举 `TRANSFER_PARTNER` 存在" → 采纳"核销走既有 recon"；实际三条创建路径全硬拒。**枚举在 ≠ 路径通**。
- "客户侧计提同构同病" → 采纳；下一轮被事务顺序论证打回。**"同构"要看触发时序**。
- "`run_worker_for_tenant` 接 factory 会自锁 007" → 采纳并错修；后两轮评审家把"计划文本自洽"当"前提成立"继续放行。
- 反向：qoderclicn 称某 SQL 常量全库无匹配（它的 grep 失败，符号就在 service.py）；reasonix 疑某列非 PG enum（schema.sql 里就是）。
  **否证也要亲验**。

规则：
1. 每条拟采纳的 P1（无论哪栏、无论几家一致），Claude 先 Read/Grep **前提**（不是结论）：它说的文件/函数/枚举/
   路径/时序在当前工作区是否真是那样。裁决行必须带**自己核对的** `文件:行号`，不得转抄 agent 给的行号。
2. 多家一致不等于成立——它们看的是同一份文本，会一起被文本自洽骗过。
3. agent 之间矛盾时**以代码为准**，不以家数或口吻为准。
4. 亲验不成立 → 驳回并写明"因 X 不成立"，同时检查自己上一轮是否已按它改过文档（有则回滚那段）。

红旗（看到就停下亲验）：`"既有 X 可复用"` / `"与 Y 同构"` / `"全库无匹配"` / `"必然自锁/死锁"` /
`"前一轮已修，本轮确认闭合"`（评审家常把回流后的自洽文本当作前提成立）。

## 1. 一致性矩阵（全量模式）

> 参与方 = 外部 agent + G2 的 `self`（Claude 的 fresh-subagent），`self` 在矩阵里与外部各家平权。
> 仅**全量模式**（每个 agent 都看全部）适用一致性矩阵。**分工模式**下各 agent 看的是不同面、几乎无
> 重叠，不做矩阵——改为**按范围拼合**（下）：每一面列该负责 agent 的发现，标注"此面仅一个模型看过、
> 无交叉验证"，Claude 对高风险面可自己补看或另指一个 agent 复核。

把各 agent 的发现去重、按主题归并，标注覆盖度：

```
跨模型一致性
┌──────────────────────────────┬────────┬──────────────────────────┐
│ 发现 / 结论                   │ 覆盖   │ 来源                     │
├──────────────────────────────┼────────┼──────────────────────────┤
│ auth.ts:47 令牌过期返回 null  │ 都发现 │ codex, gemini, codebuddy │
│ 列表渲染 N+1 查询             │ 多数   │ codex, reasonix          │
│ 缺少并发写锁                  │ 仅 1   │ codex                    │
└──────────────────────────────┴────────┴──────────────────────────┘
```

覆盖度定义（设参与 agent 数为 n，**含** G2 的 self）：**都发现 = n/n**；**多数 = 过半但非全部（> n/2）**；
**少数 = 2 个但未过半**；**仅 1 = 1/n**。n=2 时只有"都发现(2/2)"和"仅 1(1/2)"两档，没有"多数"。

- **都发现**（全部参与 agent 一致）→ 高置信，优先处理。
- **多数发现** → 较可信。
- **仅 1 个发现** → 需 Claude 独立判断真伪：读对应代码确认，别盲信也别盲弃——
  单模型独有的发现既可能是幻觉，也可能是别人漏掉的真 bug。

## 2. Claude 的裁决

对每条结论给出：**采纳 / 存疑 / 驳回** + 一句理由（最好带自己核对过的文件:行号）。
分歧点单列一节说明谁对谁错、为什么。

```
裁决
- ✅ 采纳：auth.ts:47 空值——已核对，令牌过期确实返回 null，会白屏。
- ✅ 采纳：N+1 查询——list.ts:88 循环内查询，50 条约 +200ms。
- ⚠️ 存疑：并发写锁——仅 codex 提出；当前为单实例部署，暂不阻塞，记为遗留项。
- ❌ 驳回：gemini 说的"未处理超时"——实际 http.ts:20 已有 timeout，误报。
```

## 3. PASS / FAIL 门禁（review / 文档评审模式）

- 综合后**存在任一被 Claude 采纳（且已按 0.6 亲验成立）的 P1 / critical 问题** → **GATE: FAIL**。
- 仅 P2/P3 或无问题 → **GATE: PASS**。
- codex 原生 review 输出里的 `[P1]` 标记同样计入。
- **只算已查证的**：未经 0.5 回填、仍停在"需核实假设"的条目**不计入门禁**（但要在结论里列出来）。
  某个 agent 因看不到代码给的整体"FAIL / unverifiable premise"**不直接采纳**，按 0.5 拆开核实。

```
GATE: FAIL（2 个已确认 P1）
  1. auth.ts:47 令牌过期空值
  2. api.ts:63 未校验外部输入
```
或
```
GATE: PASS（仅 P2/P3，可择机改进）
```

FAIL 时：列出必须修的项，询问用户是否让 Claude 修复（修复由 Claude 执行，之后可再跑一轮
review 验证）。

## 4. Claude vs 外部 agent 对比（凡有 G2 `self` 参与的模式必做）

数据来自 G2 的 `self`（本对话此前若还跑过 `/code-review`，其发现并进 self 一侧）。固定一段：

```
Claude vs 外部 agent
  双方都发现：<...>
  仅外部 agent 发现：<...>   ← 值得重点看，Claude 的盲区
  仅 Claude 发现：<...>
  一致率：X%（N/M 条唯一发现重合）
```

## 5. brainstorm / challenge 的综合形态

- **brainstorm**：产出「取舍表（各方案优劣）+ 风险清单 + 推荐方案及理由」。不同 agent 给了
  不同架构时，明确对比而不是简单拼接。
- **challenge**：产出「攻击面清单」，每项标 真问题 / 已被现有代码处理 / 存疑，并给
  Claude 的加固/补测试建议。

## 6. 多轮回流协议（`--round N`，spec / 计划 / 代码评审通用）

实际使用里一份 spec 平均要 3-5 轮外审才收敛；没有协议时每轮都在重复三类事故：忘了让 agent 回归核对上一轮、
回流后新写的段落没人看就进下一轮、补丁式 string-replace 堆到第四轮文本破碎。协议：

**每轮的顺序**
1. **自查（G1，每轮，在发外审之前）**：由 fresh-subagent 执行，不是 Claude 自己（做法见 §6.1）。第 1 轮看评审对象本身；
   N ≥ 2 时只看上一轮回流
   **新写/改写的段落**——评审收敛后那一版最危险，因为新写入还没被任何人读过。检查：与其它章节是否矛盾、被改的概念是否
   **全文 grep** 同步（改了一个名字/口径，其它 N 处引用要一起改）、连续补丁堆出来的段落是否已破碎（是 → 整段重写）。
   自审的"必须修"由 Claude 亲验后改进文档，记入版本。
2. **外审提示词**：标题带"第 N 轮"；附「回归核对」段（上一轮已采纳发现清单 + 本轮改动章节）+ 新一轮「核实清单」
   （优先挑本轮新写入里的断言）。agent 组合可缩：连续两轮无 P1 的 agent 可换成另一家，换视角。
3. **综合**：0.5 回填 + 0.6 亲验 → 矩阵 → 门禁；结尾写 **本轮已核实 P1 数** 与上一轮对比。
4. **回流**：受伤段落整段重写；版本号 +0.1；按 [changelog.md](changelog.md) 调用 `prowler-changelog` 逐项记录实际修改与验证状态，
   commit 信息列本轮回流项，具体文件列表包含对应日志；再问用户是否开下一轮。

**收敛判据（满足其一即停，剩余项转"实施期核实"清单）**
- 连续两轮 **已核实 P1 = 0**；
- 或 P1 数不再下降（如 1 → 1）且剩余都是需要运行/压测才能判定的项；
- 或第 5 轮仍有 P1 → 停下，与用户一起看是否是 spec 范围本身有问题，别靠加轮次磨。

**记录**：综合结尾固定一行 `轮次 N ｜ 参与 <agents，含 self> ｜ 无效 <agent:类别> ｜ 已核实 P1 <k>（上轮 <j>）｜ Claude vs 外部一致率 <x%> ｜ 结论 <继续/收敛>`；
随后逐条 `codev_finding_add <仓库名> <文档 slug> N <agent> <模型> <编号> <P1/P2/P3> <A/B> <采纳/驳回/存疑> <成立/不成立/待定> <独家/共同> "<一句话>"`。

### 6.1 自查（G1）用 fresh-subagent——每轮，含第 1 轮

不是 Claude 自己再读一遍。写出那段文字的上下文对它是盲的（"评审收敛后那版最危险"的根因）。用 Agent 工具起一个
不带本对话上下文的 general-purpose subagent，给 prompts.md「自审模板」（文档路径 + 本轮 diff + 上一轮编号清单）。
它的"必须修"由 Claude 亲验后改进文档，改完才发外审。它的发现编号 `r<N>-check-<序号>` 并记台账（agent 写 `check`）。
第 1 轮同样要做（SKILL 通用机制 G1）：没有上一版 diff，就把评审对象本身当 diff 给它。

### 6.2 已驳回清单

每轮把 0.6 亲验驳回的发现连同依据写进下一轮提示词的「回归核对」段。作用是防震荡：第 4、5 轮常见的情形是上一轮驳回的
被另一家重新提出，没有清单就会再核一遍、再驳一遍。agent 若带**新的代码证据**重提，仍要亲验，不能因为在清单里就无视。

### 6.3 `--auto` 自动多轮

开始时 AskUserQuestion 一次，确认三件事：agent 组合、轮次上限 K（默认 3，最多 5）、预算提醒（每轮约消耗多少额度，按账本近期用时/成本估）。
之后每轮：G1 自查（6.1）→ 外审 + G2 自评（并行）→ 0.4-0.6 → 矩阵/门禁 → 回流 → `codev_archive` + `codev_commit_round` → 打印记录行 → 判停。

**停止条件**（任一满足即停，停时把剩余 B 栏/待定项写成"实施期核实"清单交给用户；与上面的收敛判据同口径）：
1. 连续两轮已核实 P1 = 0 → **已收敛**；
2. 本轮已核实 P1 数 ≥ 上一轮（不再下降）**且剩余 P1 都是需要运行/压测才能判定的项** → **已收敛**；
   不再下降但剩余 P1 仍可静态修复 → 不算收敛，再跑一轮（这条防的是"P1 从 1 变 2 就停"的过早终止）；
3. 任一参与的外部 agent 本轮类别为 `quota`/`auth`（额度耗尽后继续跑只剩单模型，不如停下等重置）→ **停止但未收敛**；
4. 有效参与的外部 agent < 2（self 不计）→ **停止但未收敛**；
5. 到达 K → **停止但未收敛**（除非同时满足 1 或 2）。
记录行的"结论"字段写 已收敛 / 停止未收敛，别把 3-5 说成收敛。
**不得**为了凑收敛而降低亲验标准或跳过自审；也不得在停止后自行加轮。每轮回流都已 commit，用户随时可回退某一轮。

## 原则

- **忠实**：综合是 Claude 的判断，但不得篡改或曲解 agent 原文（原文已在上方逐字呈现）。
- **暴露分歧**：模型间不一致的地方要显式点出，这通常比一致的地方更有价值。
- **可执行**：每条采纳的结论都要能落到"改哪个文件、怎么改、怎么验证"。
- **注明参与方**：结尾写清本轮实际参与的 agent 及被跳过的 agent。
- **区分"没查证"与"有缺陷"**：这是本文件最容易被违反的一条。agent 说"无法验证"时，
  正确动作是**去验证**（0.5 节），不是把它当成一个缺陷记下来。
- **区分"agent 说已查证"与"真的成立"**：第二容易违反的一条（0.6 节）。采纳 P1 前自己看代码。
