# codev 评审协议 v2

状态：v0.2 草案；协议实现待开始；判断组最多两个 agent，评审组可多个

## 1. 目标与范围

按用户确定的流程，将 codev 调整为：选择评审者与判断者 → 首次主 agent 工作 → 独立评审 → 判断并取一致意见 → 修复 → 修复后 self review → 自动提交，不自动 push。

本 spec 是后续实施依据，不代表现有 `SKILL.md`、脚本或账本已迁移。它替代旧协议每轮前置 G1 加并行 G2 的固定安排；原有只读边界、调用超时、失败分类、用量记录和敏感内容扫描继续保留。

本次设计覆盖评审与判断的职责、首次执行、版本和材料交付、回流验收、发现去重及兼容、changelog 和提交。共享证据包及按需裁剪副本属于后续实验；不在第一阶段全面启用，不承诺固定 token 降幅。

## 2. 已确定规则与执行口径

用户已确定：

1. 开始时选择可用的评审 agent 和结果判断 agent；评审组可多个，判断组最多两个，判断者主要是 Claude、Codex
2. 首次调用先进行当前主 agent 的工作，后续调用不重复此步骤
3. 等待评审结果后综合，再由判断者裁决；多人判断时，只执行一致意见
4. 指定判断者就是当前主 agent 时，由主 agent 判断；指定了不同判断者时，主 agent 也必须参与
5. 根据最终判断修复；修复后做 self review，避免简单逻辑错误
6. 每次修改后自动 commit，不自动 push
7. 保留独立复核权；所有未解决 P1 都纳入放行条件，包括回流造成的 P1

**人数规则**：「最多两个 agent」仅限制最终判断组（包含主 agent，身份去重后计数）。评审组可以选择多个 agent，不设固定两人上限，具体数量由任务需要、可用性和预算确定。例如评审组可以为 Codex + reasonix + codebuddy，判断组为 Claude + Codex；整个任务的参与主体并集不受两人上限约束。

「首次」按同一评审任务的首次执行解释，而不是每次输入 `/codev` 都重新算首次，也不是机器安装 skill 后全局只执行一次。任务标识和恢复规则见 §4。

「每次修改」按一次完整的逻辑修改批次解释，而不是一次 Edit 调用或一行替换一个 commit。首次工作产生的修改、判断后的修复、self review 引起的补修分别形成可追溯批次。

## 3. 角色、选择和判断规则

### 3.1 角色

| 角色 | 职责 | 修改权限 |
|---|---|---|
| 主 agent M | 理解任务、首次工作、组织材料、参与最终判断、修复和提交 | 当前任务中唯一写入者 |
| 评审组 R | 独立检查同一版本，输出问题、证据、建议与覆盖范围 | 只读 |
| 判断组 J | 对去重后的问题逐条判断事实、处置及修法 | 只读；M 以判断角色工作时也先输出裁决 |
| self review | 修复后的一次明确复查阶段，核对实际修复和简单逻辑 | 先只读检查，再由 M 补修 |

角色不等于额外模型调用。同一个主 agent 不因兼任判断者而再起一个同身份的“第二票”；评审输出也不能直接当成判断票。取消每轮固定增加一个 G2 的要求。

这里的 agent 身份按执行主体识别，例如 Claude、Codex；具体模型 ID 另外记录。同一主体的两个上下文或两个模型版本不能伪装成两个独立判断主体。

### 3.2 选择

开始时展示可用性、读取能力和近期失败情况；分别确定评审组、判断组、范围、轮次与预算。用户已经指定的选择直接沿用，后续轮次不重复提问。

评审组至少一个，可选择三位或更多；仅一个时记录独立交叉覆盖有限。评审者增加不增加最终判断票，判断组不得增加第三个主体。判断者不可用时，不把超时、空输出、额度不足当成同意，也不自动缩减原定判断组。

首次工作后才封存评审材料；所有选中的评审者完成或被明确归类为失败后，进入综合。必要参与者失败且不能完成原定覆盖时，输出“覆盖未完成”，可保存已取得的结果，但不宣称通过。

### 3.3 最终判断组

最终判断组为主 agent M 与用户指定判断者集合的并集，去掉重复身份，J 最多两个。评审组的人数不计入这一上限；兼任判断者的评审 agent 按其判断身份计入 J。

| 主 agent | 指定判断者 | 最终判断组 | 执行条件 |
|---|---|---|---|
| Claude | Claude | Claude | Claude 明确采纳 |
| Claude | Codex | Claude、Codex | 两者对同一方案明确同意 |
| Claude | Claude、Codex | Claude、Codex | 两者对同一方案明确同意 |
| Codex | Claude | Codex、Claude | 两者对同一方案明确同意 |
| Codex | Codex | Codex | Codex 明确采纳 |
| 非 Claude/Codex 的 M | Claude、Codex | 将产生三个主体 | 选择冲突；调整选择后再开始，不能绕过主 agent 或偷偷加第三票 |

### 3.4 一致意见的单位与分歧

一致意见按稳定问题 ID 和具体处置逐项判断，不按整份报告的 PASS/FAIL，也不只比较“都认为有问题”。每条判断包含：事实成立与否、严重级别、修复范围、选定修法、验收条件及证据版本。

- 两人均采纳且同意相同修复范围与修法：进入执行清单
- 两人均否定缺陷，且给出相容证据：关闭该项，保留驳回依据
- 同意有缺陷但修法不同：保留缺陷为 open，修法为 disputed，不执行任意一方的方案
- 一人采纳、另一人驳回/存疑/未返回，或只同意一部分：只处理明确达成一致且可独立执行的部分，其余保留分歧
- 严重级别不一致且涉及 P1：在澄清前仍按潜在阻塞项保留；不能通过取较低级别绕过门禁

多位判断者先基于同一材料独立出结果，再展示差异；允许对分歧补证后重新判断，禁止用措辞替另一位补出“同意”。对已判断方案的实质扩展必须回到判断阶段，不能借修复名义增加未达成一致的改动。

## 4. 任务身份、首次工作与恢复

任务状态在目标仓库的本地任务目录持久化，任务键由规范化仓库位置、评审对象/范围和模式确定，并分配稳定 task ID。相同对象恢复评审沿用原 task ID、累计轮次和预算；改变任务边界或用户显式开启新任务才新建。

状态至少记录 `task_id`、对象范围、主 agent、R/J、`initial_work_completed`、累计轮次、当前阶段、快照 ID、预算消耗和最后一次提交。

首次工作由 M 完成，与模式一致：文档评审先读文档和必要代码、形成初步判断；方案任务先形成初稿；已授权实现任务先完成初始修改。不能仅因评审请求而自动实现一个新功能。

首次工作全部完成并保存产物/检查结果后才写 `initial_work_completed=true`。中途失败或被打断时恢复未完成阶段；缺失状态不能被解读为“首次工作已完成”。同任务的新一轮、重新调用 skill 或切换执行会话都不重复已完成的首次工作。

初始修改按 §10 自审、记录并提交。没有文件修改则保存任务状态，不制造空 commit。初次自查并不替代后续每次修复后的 self review。

## 5. 每轮流程

1. **选择/恢复**：按 §3 确定角色，按 §4 识别首次执行；完成必要的首次工作
2. **封存材料**：保存不可变的评审快照、完整差异和材料清单，完成读取检查和扫描
3. **独立评审**：调用 R，读取同一快照；等待结果并记录覆盖/失败状态
4. **综合与判断**：去重但保留全部来源，收集 J 的明确判断，生成执行清单与分歧清单
5. **修复**：M 只实施已达成一致的修法；保存修复后的快照及实际 diff
6. **修复后 self review**：对照执行清单检查最终文本/代码，运行适当验证，处理简单错误；补修的差异继续做定向复核
7. **记录与提交**：更新发现状态、changelog 和快照记录，自动提交本批实际修改，绝不自动 push
8. **判停/续轮**：按 §9 判断通过、继续或停止未完成；已有轮次与预算授权内自动续轮

外审、判断和 self review 的只读阶段，不允许 M 或其它参与方同时修改正在被读取的材料。当前工作区出现并行修改时保持旧快照可用；修复前检测目标文件是否仍匹配预期，不能覆盖他人改动。

## 6. 固定版本与完整材料交付

### 6.1 快照是差异的依据

为每轮保存至少三个明确版本：

- `review_snapshot`：所有评审者和判断者共同读取的版本
- `repaired_snapshot`：执行清单落地后的版本
- `verified_snapshot`：self review 及补修定向复核完成的最终版本

快照记录文件清单和内容哈希，覆盖范围内的 tracked、staged、unstaged、untracked，以及删除文件。可使用内容寻址副本或独立 Git 对象；不得通过暂存全部文件、提交无关 WIP 或修改用户索引来制作快照。

本轮修复 diff 固定为 `review_snapshot → repaired_snapshot`；补修 diff 固定为其实际前后快照；跨轮变化固定为 `上一轮 review_snapshot → 本轮 review_snapshot`。不能把上一轮回流后的 commit 当作其回流前版本，不能在提示词里留下会变化的 `HEAD`。

轮次号用于定位记录，不代替版本标识。相同轮次内若有多次提交，必须用阶段及快照 ID 区分。

### 6.2 材料包

每个 agent 获得可验证的材料清单：任务/轮次、快照 ID、目标文件路径及哈希、完整 diff 或分块清单、相关历史问题与验收条件、当前有效决定、读取方式、范围与缺失项。

有文件读取能力时提供只读文件；无 Git 历史时交付编排器从固定快照生成的 diff；只能接收文本时内联必要材料，不能只发无法访问的路径。不同工具看到的内容必须属于同一版本。

diff 大于单块预算时，按文件、章节或完整逻辑片段分块，保留修改前后文和稳定块 ID。15KB 可作为单块目标，不是全部上下文预算；遇到单条巨行，按文本边界切分并标明续块，不截断数据。

所有块都要在覆盖清单中有去向和读取结果。可以在已选 R 的多个评审者之间分工，但必须指定跨块/跨章节契约检查；分工数量不受判断组两人上限约束，仍须遵守已选角色和预算。超出总预算时分批在同一快照上审查，或标记覆盖未完成，不能退化为 `--stat + 主 agent 摘要` 后宣称全量覆盖。

### 6.3 文档与历史

spec 只保留当前契约、有效决定和短状态行。完整评审史移入 changelog/轮次归档，不能继续在状态行叠加整段回流记录。

历史迁移本身要作为一次逻辑修改记录和提交，验证有效决定未被误删。下一轮只取相关采纳项、未关闭项、驳回依据和验收条件；不默认加载整份 changelog，也不禁止按需查看必要历史。

## 7. 执行清单与修复后 self review

执行清单至少含：稳定问题 ID、对应判断、待改位置、依据、具体修法、关联定义/调用方/测试、验收条件。未取得必要判断票的项不能标为可执行。

修复后逐项对照真实 diff：清单内未落地的是漏改；清单外的 hunk 先标“未解释改动”，核实是否为必要连带同步。超出已同意修复范围的部分回到判断阶段。

self review 由 M 执行一个独立于写入过程的复查阶段，至少重新读取最终产物与相关上下文，不以修改脚本成功或刚才的记忆代替验收。默认不额外固定调用 G2；如用户选择独立检查者，须沿用已选参与者并遵守预算，记录其身份和用量，其结果不增加新的最终判断票；判断组仍最多两个 agent。

必查事项：

- 条件、状态机、返回类型、空值处理、单位和数值例子的简单逻辑
- 同一概念是否全文同步，是否存在相互矛盾的旧表述、重复定义、错序号和悬空引用
- 新写入的每条代码事实是否有当前版本证据，不仅检查最初被标为 P1 的发现
- 每项承诺的修复、迁移/回滚分支和验证是否有实际落点
- 代码修改运行与风险匹配的测试；文档修改核对契约、示例和引用，必要时执行可安全验证的示例

发现不改变已同意修法的机械遗漏或简单实现错误，可以按该修法补修；补修后只复核新差异和受影响的不变量。发现新行为要求、新修法或真实分歧，回到判断阶段。

不能在“self review → 修复”后立即宣称完成。最后一次修改也必须通过定向复核。定向复核受任务预算约束，达到预算仍有问题时标记未完成，而非无限补修或降低标准。

## 8. 发现身份、分类及旧数据兼容

### 8.1 分开发现来源、成因和状态

同一逻辑问题分配稳定 `issue_id`；每位 agent 的原始条目保留 `observation_id`，多位来源关联同一问题。跨轮再次出现沿用 issue ID，记录 reopen 事件，不能每轮重新计为独立新缺陷。

核心字段：task ID、issue ID、observation ID、来源 agent/模型、证据快照、严重级别、成因、判断结果及版本、处理状态、修复和验证快照、关联提交。

成因值：`existing`（原对象已有）、`introduced`（本任务修改引入）、`scope-added`（范围新增）、`unknown`（证据不足）。`reopened` 是状态事件，不与成因混成一列。归因必须比较前后证据；不能把 G1/self 来源自动判为 introduced。

状态区分 open、disputed、deferred、resolved、rejected。写过修复不立即 resolved；对应验收在最终快照通过后才能关闭。P1 转 deferred 不解除阻塞。

### 8.2 兼容策略

保留原 13 列 `findings.tsv` 的读取与旧接口调用语义；新结构带显式 schema version，采用可兼容扩展或独立结构化事件文件。实施时统一选择一种格式，并同步 writer、reader、stats、归档与测试，不能只改写入函数。

旧行没有 issue ID、成因或关闭状态时视为未知，不能自动当作 resolved，也不能凭一句话模糊匹配后静默合并。迁移可建立人工确认的映射，保留原始记录；未映射的旧行单独展示为历史来源统计，不混入新任务的去重结果。

统计至少分开：来源条目数、去重问题数、各成因的问题数、未解决 P1、分歧项、重开数、覆盖缺口。保留 agent 的成立/声称比例，但不把它当成召回率或唯一事实来源选择依据。

## 9. 放行与停止

判定采用最终 `verified_snapshot`，不是修复前的 P1 声称数。

**通过**需同时满足：原定评审及判断覆盖完成；可执行清单已落实并验收；没有未解决 P1；没有阻塞决策的分歧；没有未解释的范围外改动；最终产物与验证快照一致。

来源、成因不能改变 P1 的阻塞性。非 P1 遗留项可以在 J 明确同意不阻塞后保留，写清处置和依据。对象缺陷、回流缺陷两列用于诊断返工，不用于排除门禁。

遇到判断分歧时暂停相关项的执行，允许在预算内补证。轮次结束仍存在必要参与者失败、未完成覆盖、未解决阻塞项、阻塞决策的分歧、验收失败或修复前检测到的并行改动时，标“未完成/未收敛”；达到预算或累计轮次上限则停止。不能把失败自动转换成少数人的通过结论。

有继续授权且未到上限时，可以在同任务内补证/续轮；恢复调用不重置累计预算、轮次或未解决项。需要改变角色、范围或增加预算时，明确提出所需决定，不自行加人加轮。

## 10. Changelog 与自动 commit

使用已接入的 `prowler-changelog`，依 [changelog 项目适配规则](../references/changelog.md) 按实际逻辑变更逐项记录；不套用 Prowler 组件目录、版本或 PR 链接。

每批修改保存：日期、变更 ID、阶段、对象/文件、关联 issue、真实行为变化、验证状态。完整历史不内联 spec，日志追加不递归触发新日志条目。

正常批次在 self review/定向复核完成后，连同对应 changelog 自动提交，不再逐次询问。日志、归档和提交不是验收的替代品。

若预算耗尽而存在需要保存的未完成修改，可提交明确标记 `incomplete` 的检查点，记录未解决项；该提交不得宣称通过，也不允许进入自动发布流程。Git 冲突、部分暂存或作者混合导致不能安全提交时保留现场并报告，不为满足“自动 commit”擅自改写用户工作。

只提交本批拥有的具体文件/改动；禁止 `git add -A`，不把用户已有无关或混合改动一起提交。整文件提交无法隔离同文件他人改动时，使用明确隔离的暂存方案或暂停该次提交，不能默认覆盖原暂存边界。

提交元数据至少可定位 task、round、phase、R/J、验证快照和未解决 P1。当前 commit SHA 由提交后映射记录定位，不为将自己的 SHA 写进同一提交而无限 amend。提交失败不标记本批已提交，不删除未保存记录。

**不自动执行任何 push、force push、远端发布或触发部署操作。** 本协议的自动提交授权仅限当前任务的本地修改。

## 11. 共享证据及裁剪副本实验

基线协议稳定后再实验。codev 保持一套公共协议，各 agent 的薄适配层只负责调用参数、能力探测、材料路径、输出和用量解析。适配 skill 由编排器使用，不依赖每个外部 CLI 自己支持 skill，也不把 skill 当成文件权限来源。

共享证据包必须带原始代码片段、快照、检索范围、出处及未确定前提。其它 agent 可以直接复用，也必须能追踪依赖、补取文件和挑战推断；禁止把某一位的“事实表”设为不可质疑的结论。

裁剪副本从目标文件、必要依赖和材料清单起步，提供只读补取通道；被裁剪掉的文件不得据此被判为不存在。扩充材料仍取同一快照并扫描；无法补齐时标覆盖不足，不静默换到实时仓库或寻找未授权母本。

实验保持任务、快照、角色组合和问题口径可比，记录实际模型请求数、读取范围、input/cache read/cache write/output、耗时、失败和遗漏。金额保留币种与估算标记，不把缺失用量当零，不直接相加不同 CLI 的混合 token 口径。

用已知缺陷样本检查遗漏率，配合实际任务观察；没有足够样本时不宣称召回率不变。复制文件体积与模型实际读取量分别统计。

## 12. 实施顺序与验收场景

实施顺序：

1. 按评审组可多个、判断组最多两个的规则统一角色/判断协议、任务状态、固定快照和执行清单，落实修复后 self review 与补修复核
2. 移走历史噪音，实现完整 diff 交付和覆盖记录，同步模板及代理读取检查
3. 升级发现身份、分类、状态及统计，完成旧数据兼容与全量未解决 P1 门禁
4. 接入每批自动本地提交与 changelog，验证恢复和失败路径；前述阶段的开发修改同样按用户要求提交
5. 验证基线后，试验共享证据和按需裁剪；根据请求数及遗漏情况决定是否启用

以下场景是实现验收要求，当前 spec 阶段不声称已运行：

| 场景 | 必须观察到的结果 |
|---|---|
| 首次调用、第二轮、恢复会话 | 首次主 agent 工作只完成一次；中断可恢复，预算不重置 |
| 评审组为 Codex、reasonix、codebuddy，M=Claude，指定 J=Claude、Codex | 三位评审者均可参与；最终仅 Claude、Codex 两位判断，评审意见不额外计票 |
| M=Claude，指定 J=Codex | 两者都参与最终判断；只有两者同意的具体修法进入执行清单 |
| M=Codex，指定 J=Codex | 只有一位判断主体，无重复自投票 |
| 两位判断者同意缺陷、不同意修法 | 缺陷保留 open，修法 disputed，不擅自执行 |
| 一位判断者失败或没回答某项 | 不把缺席当同意，结果标未完成 |
| 两位指定判断者均不同于 M | 选择器报告人数冲突，不生成三个判断主体 |
| 大 diff、巨行、无 Git 的 agent | 原始变更全部可读，分块完整，未覆盖部分明确可见 |
| 上一轮修改已 commit，工作树干净 | 仍能从固定前后快照得到非空回流 diff，不误比同一提交 |
| untracked、删除文件、并行改动 | 快照表达真实内容；修复前漂移被发现，不覆盖他人改动 |
| 修复留下旧类型或新事实错误 | self review 抓到；补修后继续定向复核最后差异 |
| 清单外出现 hunk | 先解释关联性；实质范围扩展重新判断 |
| 两家报同一问题、下一轮重开 | 一个 issue、多条 observation，保留重开事件和原成因 |
| 原对象 P1=0，回流 P1=1 | 不通过，不能因归类不同而放行 |
| 13 列旧账本与新记录共存 | 旧统计可读，未知状态不误判已关闭，新任务结果可去重 |
| 验收完成、验收未完成检查点 | 分别提交明确状态；changelog 同步；均不 push |
| 用户已有暂存、同文件混合改动、提交失败 | 不卷入无关改动，不破坏索引，不伪报提交成功 |
| 裁剪后需要新依赖文件 | 可从同一快照补取；失败标缺证，不判文件不存在 |

实施需同步 `SKILL.md`、`references/synthesis.md`、`references/prompts.md`、`references/agents.md`、`references/changelog.md`、库和测试，以及使用文档；不得只增加新协议段落而留下旧固定 G1/G2、强制固定评审组合或摘要降级规则继续生效。
